# 工程约定

本文写现有工程的结构、不能破坏的规则、已知的坑、验证流程和性能预算。每一步开始前读一遍。

> 2026-10-25 更新：结构表是第一版完成时的状态；第二节第 0 条在第 2 步地形重塑后改为新顺序；第四节的自查增加了参考对比、灰度和剪影测试，以及 Claude 审图；第六节的记录改为写在 `docs/记录/`，遗留合并进 03。

## 一、现有结构

### 场景

`game/scenes/main.tscn` 的节点：

```
Main
├─ WorldEnvironment        环境光、调色、泛光（参数由 SkyDirector 每帧改写）
├─ Sun                     唯一的平行光；夜里由 SkyDirector 改成月光方向
├─ Universe                所有天体的父节点，浮动原点平移的就是它
│  ├─ PlanetDawn (Planet)  晨，profile 0
│  │  ├─ Terrain (PlanetTerrain)
│  │  ├─ InlandWaters      河面与湖面（运行时添加）
│  │  ├─ Landmarks         样板区地标（运行时添加）
│  │  ├─ Wildlife          鸟、鹿、萤火（运行时添加）
│  │  └─ SurfaceDetails    植被、石块、遗迹拱门（运行时添加）
│  ├─ GasGiant             渊
│  ├─ PlanetEmber          烬，profile 1
│  └─ PlanetFrost          霜，profile 2
├─ FloatingOrigin          玩家离原点超过 2 公里时平移 Universe
├─ Player (StarSeaPlayer)
├─ SkyDirector             太阳、月亮、天气、调色、全局着色器参数
├─ HUD                     状态栏、帮助、性能面板、地图（TerrainAtlas）
├─ Soundscape              环境声、脚步、音乐
└─ VoyageMenu              开始菜单与暂停菜单
```

### 全局着色器参数

在 `project.godot` 的 `[shader_globals]` 里声明，由 `SkyDirector` 每帧写入：

`sun_dir`、`moon_dir`、`sky_up`、`surface_sky`、`star_visibility`、`rim_strength`、`shadow_fill`、`focus_center`、`focus_radius`、`wind_dir`、`wind_speed`、`cloud_offset`、`cloud_cover`、`cloud_shadow`、`rain`、`wetness`、`mist`、`mist_color`、`aurora`、`shadow_up`、`shadow_side`、`cave_factor`、`weather_time`、`valley_floor`。

地形顶点色 R 保存曲率遮蔽（0.68～1），G 保存坡度，B 保存湿度，A 保存林地权重；高度直接从球心相对位置计算。`CUSTOM0` 的地貌标记保持原有含义。接触贴花挂在 `Universe` 下，随浮动原点一起平移。草地中尺度笔触读取自绘 `meadow.svg`，近景短笔触读取 `ground.svg`；色板的 `cool_saturation` 只控制冷色补偿，结果烘焙进三维调色表。

新增全局参数时：先在 `project.godot` 声明，再在 `SkyDirector` 写入，最后在本文这张表里补上。

## 二、不能破坏的规则

0. **地形特征的叠加顺序固定**。第 2 步起：烘焙高度场（意图 + 抬升 + 火山 + 峡谷主体 + 侵蚀）→ 峡谷岩层台阶 →（第 8 步加入：温泉）→ 河道 → 文明区 → 洞穴。新特征插进这个顺序时，在本文和对应规格里同时更新。
1. **高度函数是唯一来源。** 地形网格、碰撞、地图、小地图、植被、地标、动物、飞行保护都调用 `TerrainNoise.height()`。任何改变地面高度的东西（河床、平台、道路、梯田、洞口）都必须写进高度函数，即 `TerrainNoise` 或 `TerrainFeatures`，不能只改网格或只放一块碰撞。唯一的例外是洞穴内部（洞壁是离线生成的独立网格）。
2. **高度函数必须是确定的。** 同一个方向在任何时候、任何线程、地形算没算过，返回值都一样。不能依赖"玩家走到哪里才算出来"的状态。需要大量计算的特征用离线烘焙（`tools/Bake-World.ps1`；第 2 步起还有 `tools/Bake-Terrain.py`）。
3. **出发地不动。** 出发地由 `base_height()` 选定，后加的特征不能把它淹掉、挖掉或盖住。每次改地形后，用 `ecology_runtime_checks` 的 `spawn_clear` 确认。
4. **浮动原点。** 世界里的东西都挂在 `Universe` 下的星球节点里，用以星球中心为原点的坐标。不能保存或缓存全局坐标；存档里存相对星球的坐标。着色器里需要稳定坐标时，用 `focus_center` 换成相对星球的坐标。
5. **后台线程不碰节点。** 后台任务只算数组和数据；创建节点、网格、碰撞形状都在主线程。后台线程读的共享数据必须在建好后只读，或者用 `Mutex` 保护。
6. **确定性。** 所有随机都用固定种子，按位置或编号派生（例如 `hash(key) + planet_seed`），不要用全局 `randi()`。同样的种子必须得到同样的世界。
7. **验收机位暂停时间。** `ShotCatalog` 会设置 `SkyDirector.time_paused`。此时天气保持晴天、太阳不动，`weather_time` 和云影偏移固定为零；天空云层、极光及地面风痕共用该时钟，不能直接使用持续推进的引擎 `TIME`。新加的系统也要在这个状态下保持稳定。
8. **地形块内的水面。** 海面由地形块的水面网格和 `water.gdshader` 绘制，河湖由 `InlandWaters` 绘制。不要把新的水体加进海面网格。

## 三、代码风格

- GDScript 全部写静态类型。
- 注释用中文，说明"为什么"，一行只写一条语句。
- 不留调试输出、临时探针，也不留从命令行覆盖画面参数的后门。
- 新类用 `class_name`；新建脚本后先导入一次（`godot --headless --path game --import`），否则其他脚本找不到类名。
- 参数和数值写成有名字的常量，附一句注释说明含义和单位。
- 和远行者相关的新代码放在新目录 `game/scripts/civilization/`；新模型放在 `game/models/`；新数据放在 `game/data/`。

## 四、验证

### 自动检查

发现单项失败后，可用 `-OnlyChecks` 复查对应项目，并通过 `-ReportDirectory` 保留独立报告，例如：

```powershell
& tools/Test-Acceptance.ps1 -Scope dawn -OnlyChecks @('caves', 'ecology') -ReportDirectory 'test-output/acceptance-repair'
```

定向报告会标记 `full_suite = false`，不能称为整套验收。重新验证发布包时同时选择 `build`；未知项目名称会失败。首次失败报告必须保留。

现有检查都要继续通过：

| 命令 | 内容 |
| --- | --- |
| `tools/Test-Acceptance.ps1 -Scope dawn` | 晨的全套验收，包括打包和性能（本机）。默认范围 |
| `tools/Test-Acceptance.ps1 -Scope all` | 三颗星球全部验收 |
| `ecology_checks.gd` | 群系、模型、植被约束（可无界面） |
| `ecology_runtime_checks.gd -- --check=ecology_runtime` | 运行时碰撞、出发地空地、浮动原点（可无界面） |
| `surface_checks.gd -- --check=surfaces` | 三颗星球行走与跳跃（可无界面） |
| `completion_checks.gd -- --check=completion` | 存档、菜单、设置、环境音（可无界面，环境音部分需要有声卡） |
| `camera_checks.gd -- --check=camera` | 视角与灵敏度（需要真实窗口） |

**验收范围**：按改动的大小决定跑多少，不要每一步都跑全套。

| 时机 | 跑什么 |
| --- | --- |
| 普通步骤结束 | 这一步"完成标准"里列出的检查和新机位，加上改动可能影响到的旧机位（例如改了地形着色器，就重测地表机位）。不跑连续降落、连续行走，也不打包 |
| 第 2 步（地形重塑）结束 | `tools/Test-Acceptance.ps1 -Scope dawn` 全套，包括打包、哈希核对和性能 |
| "第二版自测"和第 10 步，以及合并进 `main` 之前 | `-Scope all`。公共代码（玩家、飞船、着色器、天空、存档）的改动也会影响烬和霜 |

- 先把这一步的改动全部做完，再跑验收。跑完以后还要改，只重测受影响的那几项，不要再跑一遍全套。
- 普通步骤里，如果拿不准某个改动会不会影响别处，就多测那一项相关的检查，而不是直接跑全套。
- 结果写进那一步的记录，写明跑了哪些、没跑哪些。

### 自查、参考对比与审图

第一版的教训：自查经常用"检查通过""像素宽度达标"代替亲眼看图，结果主机位里一眼可见的问题被当成完成交了出来。所以从 2026-10-25 起，画面类的完成标准是**看图**，而且要由 Claude 审过。

每一步结束、提交之前：

1. **截图**：截这一步列出的机位，每张都和改动前同一机位并排；新做的模型按 [10](10-质感与渲染.md) 第四节出四视图、灰度图、剪影图。
2. **参考对比**：每个主机位找 2～3 张参考作品里构图相近的画面（《旷野之息》《Sable》《A Short Hike》《Firewatch》《Journey》等），拼成"参考 | 改动前 | 改动后"的对比图。参考图只放在 `test-output/reference/`，**不进仓库**（版权），记录里写来源链接；对比图里的参考部分也只留在 `test-output/`，进仓库的只放我们自己的截图。
3. **四个测试**（[10](10-质感与渲染.md) 第二节）：去色、剪影、材质、接地，逐张写判断。
4. **低级问题清单**，逐条对照，有一条就修：

   | 问题 | 怎么看出来 |
   | --- | --- |
   | 面发黑或整片纯色 | 本该受光的面是黑的、深色的一片；超过画面 5% 的纯色平面 |
   | 代码拼凑感 | 看得出方盒、球、圆柱直接拼在一起；没有倒角的锐边；大平板 |
   | 悬空、穿插 | 东西离地、陷进地里、两个物体互相穿透 |
   | 闪烁、破面、漏光 | 两个面重叠闪烁；能看穿到模型内部；缝里漏出不该有的光 |
   | 遮挡 | 本该看到的主体被栏杆、墙、岩壁挡住 |
   | 尺度不对 | 和 1.75 米的探索者比，门、台阶、雕像的大小不合理 |
   | 远处认不出 | 纪念物和巨构在规定距离（圣经第五节）外看不出轮廓 |
   | 颜色跑偏 | 和圣经第四、六节或 [10](10-质感与渲染.md) 的色板不符，或者和周围明显不协调 |
   | 重复排列 | 同样的东西整齐地重复，一看就是复制的；等距的条纹 |

5. **规格的"人工确认"项**：逐条用一两句话写出判断和依据（看的是哪张图）。
6. **Claude 审图**：把对比图的路径和第 3～5 条的判断写进记录，交给 Claude 审。Claude 不通过的项必须修，修完再审，不限轮数。审图通过才算这一步完成。只有不明显的细节、性能小幅超标可以留作遗留，写进 [03](03-现状与遗留.md)。
7. **只重测受影响的部分**：改了模型，只重新生成那几个模型、重截相关的几张图，不重跑全套。

每个新系统都要：

- 新增或扩展一个检查脚本，报告写入 `test-output/`，以报告里的 `passed` 为准；
- 至少新增一个固定机位（加进 `ShotCatalog.NAMES` 和 `place()`），用于截图和性能测量。

### 性能预算

在本机 780M、1920×1080、渲染比例 1.0、关闭垂直同步下：

- 所有固定机位：平均 ≤ 12.5 ms，P95 ≤ 16 ms。
- 从太空降落：P99 ≤ 20 ms，前 3 秒以后没有超过 50 ms 的帧。
- 主线程每帧上传地形不超过 4 ms。
- 每个新系统在它最重的机位上，相比加入前平均增加不超过 1 ms。超出时先优化；优化不了就写进记录和 [03](03-现状与遗留.md)，继续下一步，在"第二版自测"时一起交给用户决定。

常用的省法：

- 重复物件用 `MultiMesh`；
- 远处用简化网格或干脆不画（`visibility_range_end`）；
- 小物件不投影；
- 只在玩家附近生成；
- 大量计算放后台线程或离线烘焙。

### 云端会话的已知限制

如果某一步在 Claude 的云端会话里验证，注意：

- 没有显卡，用 CPU 软件渲染，一帧约 340 ms，测出的性能没有参考价值。
- 软件渲染开启 MSAA 时读不到深度纹理，大气和海面会盖住物体。云端截图时要把根视口的 `msaa_3d` 关掉。
- 地表机位等地形超过 120 秒会失败，这是渲染慢，不是代码错误。
- `camera_checks` 在无界面模式下必然失败。
- 没有声卡。

## 五、存档兼容

`journey.cfg` 的版本号目前是 1。新增字段时：

- 新字段是可选的：旧存档没有这个字段时用合理的默认值，不能拒绝读取。
- 新字段存在但不合法时，整份存档拒绝读取，不修改任何世界状态（与现有字段一致）。
- 在 `completion_checks.gd` 里补上新字段的往返测试和非法值测试。

## 六、文档与记录

为了让文档保持少而集中：

- 规格只写**要做的事**。一份规格的内容全部做完、审图通过后，由 Claude 把仍然需要长期遵守的规则并进 01、02 或 03，然后删除这份规格。
- 每一步的记录写在 `docs/记录/第N步-名称.md`，包含：
  1. 做了什么；
  2. 和规格的出入，以及原因；
  3. 自动检查结果，包括报告里的关键数字；
  4. 机位截图路径、对比图路径与性能；
  5. 自查判断（第四节第 3～5 条）和 Claude 审图结果；
  6. 遗留问题。
- 记录里的遗留问题，在这一步结束时合并进 [03 现状与遗留](03-现状与遗留.md)（写明哪一步会处理）；做完的遗留从 03 删掉。
- 进仓库的截图放 `docs/images/<步骤>/`，只放对比图需要的我们自己的截图，每张压到 1 MB 以内（JPEG 质量 85 即可）。
- 每个里程碑（第二版自测、第 10 步）之后，由 Claude 删除已经合并完的记录和图片，`docs/` 下只保留当前有效的文档。
- 只能在本机确认的事项（性能、听感），汇总到里程碑的记录里交给用户。
